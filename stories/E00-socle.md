# E00 — Socle technique & walking skeleton — User Stories

> EPIC : [EPIC-00](../epics/EPIC-00-socle-technique.md) · Jalon J0 · Réfs : `guide-architecture.md`, ADR-0002/0003/0005.

### E00US001 — Initialiser le monorepo + gestionnaires
*En tant que* développeur, *je veux* un dépôt structuré `backend/` + `frontend/` avec l'outillage, *afin de* démarrer sur des bases saines.
- **CA** : `uv` gère l'environnement Python ; `pnpm`+`Vite` initialisent le front ; `README` de démarrage ; versions figées.
- **Notes** : arborescence conforme au `guide-architecture.md` §3.
- **Dépend de** : —

### E00US002 — Configurer la qualité
*En tant que* développeur, *je veux* lint/format/typage automatiques, *afin de* garantir la qualité dès le 1er commit.
- **CA** : ruff (lint+format) + mypy strict côté Python ; ESLint + Prettier + TS strict côté front ; hooks **pre-commit** actifs.
- **Notes** : configs partagées et versionnées.
- **Dépend de** : E00US001

### E00US003 — CI bloquante
*En tant que* équipe, *je veux* une CI qui bloque le merge si la qualité échoue, *afin de* protéger la branche principale.
- **CA** : pipeline exécutant lint + typage + tests ; merge impossible si rouge.
- **Notes** : rapide (< quelques min) pour ne pas freiner.
- **Dépend de** : E00US002

### E00US004 — Squelette de couches + garde-fou d'imports
*En tant que* développeur, *je veux* les couches `domain/application/infrastructure/api` posées, *afin de* respecter l'hexagonal.
- **CA** : les 4 couches existent ; une règle (lint d'imports) **échoue** si `domain/` importe un framework ou une couche externe.
- **Notes** : cf. ADR-0003 ; test automatisé de la règle de dépendance.
- **Dépend de** : E00US001

### E00US005 — Composition root minimale
*En tant que* développeur, *je veux* un point de câblage explicite, *afin de* voir toutes les dépendances en un endroit.
- **CA** : `bootstrap/` assemble adapters + services ; aucun conteneur DI ; `main.py` démarre via le bootstrap.
- **Dépend de** : E00US004

### E00US006 — Connexion SQLite (WAL) + migration initiale
*En tant que* développeur, *je veux* la base opérationnelle en WAL avec migrations, *afin de* persister les données.
- **CA** : base créée en mode **WAL** ; **Alembic** applique une migration initiale ; connexion via un adapter d'infrastructure.
- **Notes** : cf. ADR-0005.
- **Dépend de** : E00US005

### E00US007 — File d'écriture + writer unique
*En tant que* système, *je veux* sérialiser les écritures via une file, *afin d'*éviter les `database is locked`.
- **CA** : une commande d'écriture est mise en file et exécutée par **un seul worker** ; l'appelant obtient le résultat (future) ; les lectures restent concurrentes.
- **Notes** : point de passage unique pour audit + diffusion (ADR-0005).
- **Dépend de** : E00US006

### E00US008 — Canal WebSocket + diffusion post-commit
*En tant que* client, *je veux* recevoir les mises à jour en direct, *afin de* voir l'état sans rafraîchir.
- **CA** : un client peut s'abonner ; après commit d'une écriture, un événement est diffusé aux abonnés.
- **Notes** : diffusion déclenchée depuis le writer unique.
- **Dépend de** : E00US007

### E00US009 — Repository + endpoint de bout en bout
*En tant que* développeur, *je veux* un aller-retour complet API↔domaine↔DB, *afin de* valider le patron.
- **CA** : un agrégat trivial est créé via un endpoint (DTO Pydantic), persisté par un repository (port/adapter), relu ; erreurs typées mappées à la frontière.
- **Notes** : sert de gabarit pour les US métier ; cf. ADR-0007.
- **Dépend de** : E00US007

### E00US010 — Shell React
*En tant que* utilisateur, *je veux* une app front qui charge et se connecte, *afin d'*interagir.
- **CA** : shell React+TS ; **React Query** configuré (fetch/cache) ; **Zustand** pour l'état UI ; client **WebSocket** branché ; organisation par features.
- **Dépend de** : E00US009

### E00US011 — Tranche verticale démontrable
*En tant que* PO, *je veux* une démo bout-en-bout, *afin de* valider l'architecture tôt.
- **CA** : créer un tournoi → ajouter 1 archer → le placer sur 1 cible → saisir 1 score → **voir un classement se mettre à jour en live**.
- **Notes** : versions minimales, jetables/évolutives ; sert de fil rouge pour J1.
- **Dépend de** : E00US010

### E00US012 — Exécutable de dev
*En tant que* équipe, *je veux* lancer l'app en un binaire, *afin de* préparer le packaging.
- **CA** : FastAPI sert le **build front** en statique ; un exécutable de dev démarre le tout ; port fixe.
- **Notes** : base d'EPIC-11 (packaging complet PyInstaller).
- **Dépend de** : E00US011

### E00US014 — Outiller les tests du front
*En tant que* développeur, *je veux* pouvoir **tester la logique du front**, *afin qu'*une régression sur un calcul d'argent ne parte pas en production sans un signal.
- **Contexte** : **[DETTE-005](../docs/dette.md)** — le front n'a **aucun runner** (`package.json` : ni `vitest`, ni script `test`) ; E00US002 n'a outillé que lint/format/types. Tant que le front ne faisait que du rendu, `tsc` + ESLint suffisaient. E01US010 y a introduit la **conversion euros ↔ centimes** ([ADR-0012](../docs/adr/0012-argent-en-centimes-entiers.md)), seule logique arithmétique du front — et elle décide de ce que paiera un archer (EF-8.1).
- **CA** : un runner installé (**vitest**, déjà transitif via Vite) + script `npm test` ; **branché sur la CI bloquante** (E00US003) au même titre que lint/types ; dépendance déclarée dans `package.json` **et** documentée dans [`dependances.md`](../docs/dependances.md) (ADR-0009) ; `format.ts` couvert — `0`, `« 8 »`, `« 8,1 »` → 810, `« 0,05 »` → 5, point vs virgule, rejets (`8,105`, `-8`, `huit`, `8,`), **stabilité de l'aller-retour** ; marqueur `DETTE-005` retiré et ligne déplacée en « Dette résorbée ».
- **Notes** : ⚠️ **à faire avant E08US001**, qui consommera le tarif pour calculer les montants dus. Le vrai risque de l'US est le **lockfile** : `npm ci` a déjà cassé la CI front sur une résolution `@emnapi` — revalider `npm ci` **localement** après l'ajout, et figer par `overrides` si besoin. Ne pas viser une couverture du rendu (pas de testing-library dans cette US) : le besoin prouvé est la **logique pure**.
- **Dépend de** : E00US002, E00US003 · **Jalon** : J1 *(dette — avant E08US001)*

### E00US013 — Factoriser les briques d'UI partagées du front
*En tant que* développeur, *je veux* que l'affichage d'une erreur ait **un seul point de vérité**, *afin qu'*un changement de rendu (couleur, ton, accessibilité) se fasse une fois et non dix.
- **Contexte** : **[DETTE-004](../docs/dette.md)** — `MessageErreur` est copié **à l'identique** dans 10 features (`admin`, `archers`, `bareme`, `blasons`, `categories`, `clubs`, `competition`, `gabarits` ×2, `grain-validation`) : même signature, même corps, mêmes classes, même `role="alert"`. **Tenir le compte à jour ici** : la liste est le CA, et une liste périmée fait cocher « zéro copie restante » à qui en laisse deux.
- **CA** : `MessageErreur` vit dans `frontend/src/shared/ui/` ; **les 10 copies locales** le consomment, **zéro restante** ; le rendu est **inchangé** à l'écran (mêmes classes, même `role="alert"`) ; marqueurs `DETTE-004` retirés et ligne déplacée en « Dette résorbée ». **Les 8 autres `role="alert"` du front sont examinés et tranchés explicitement** (repris ou laissés, mais pas oubliés) :
  - **4 blocs de confirmation** — ton **neutre**, pas de `--erreur`, une action : `competition/TrancheVerticale.tsx` (« Inscrire quand même ») et `archers/Archers.tsx` ×3 (« Enregistrer quand même », « Changer quand même de catégorie », « Supprimer définitivement, avec ses résultats » — ce dernier en `--danger`, sa confirmation détruit, [ADR-0016](../docs/adr/0016-supprimer-un-archer-engage-plutot-que-le-refuser.md)). **Ce sont eux le vrai enjeu** : n'ayant pas `--erreur`, un token posé sur cette classe ne les atteint pas, et un `grep MessageErreur` ne les trouve pas ;
  - **4 rendus d'erreur ad hoc** portant déjà `carte__etat--erreur` : `admin/ConnexionAdmin.tsx` ×2 (« Accès admin injoignable », « Les deux mots de passe ne correspondent pas »), `competition/TrancheVerticale.tsx` ×2 (« Montant en euros attendu », « Classement injoignable »). Un token CSS les atteint ; une refonte du **balisage** non.
  > **Compte de référence, à recompter plutôt qu'à croire** : `grep -rcn 'role="alert"' frontend/src --include=*.tsx` → **18** = 10 copies + 8 ci-dessus. Ce décompte a déjà été faux **deux fois** (à 9→10 features, puis à 3→4 blocs) : recompter avant de cocher, ne pas recopier ce nombre.
- **Notes** : refactor **mécanique et d'un bloc**, pour que la revue porte sur l'équivalence du rendu. Placée **juste avant E01US016** (identité visuelle) et le thème sombre, qui consommeront les tokens de couleur — l'alerte doit être **ambre** (`DV-03`), et ce token ne doit s'appliquer qu'à **un** endroit. ⚠️ Le front n'a **aucun test** : vérifier à l'écran (au moins la connexion admin et une erreur de saisie).
- **Livré (21/07/2026, règle 9 — décompte et décisions reversés ici)** : les chiffres du CA ci-dessus (« 10 features », « 18 = 10 + 8 ») étaient l'**estimation périmée** que cette US a corrigée **en recomptant** — précisément le piège que le CA annonçait, désormais refermé. Décompte terrain (`grep 'function MessageErreur'`) : **18 définitions dans 17 features** (`gabarits` en a 2) + le rendu **inline verbatim** de `postes/Postes.tsx` = **19 rendus** ralliés à `shared/ui/MessageErreur.tsx`, **zéro restant**, rendu inchangé. La liste du Contexte citait `competition` (disparu, relocalisé en `tournois` par E00US015) et ignorait `departs`, `inscriptions`, `placement`, `poste`, `saisie`, `scoreurs`, `scoreur-session`, `tournois`, `paiements`. **Autres `role="alert"` tranchés** : blocs de **confirmation** à action (`archers/Archers.tsx` ×2, `archers/NouvelArcher.tsx` — ton neutre, pas `--erreur`) **laissés** (ce ne sont pas des erreurs) ; le refus 409 **ambre** de `placement` (`placement__alerte`, helper `messageErreur` local) **laissé** (rendu délibérément distinct). `ErreurApi` retiré des imports devenus morts (15 fichiers), conservé là où il sert encore (`departs`, `saisie`, `placement`, `archers`, `NouvelArcher`). Aucun changement de CSS/token : l'ambre `DV-03` reste à E01US016 ; cette US centralise le **balisage** du rendu d'erreur générique — le token s'appliquera via la classe CSS `carte__etat--erreur`, déjà partagée par les rendus ad hoc restants.
- **Dépend de** : E00US011 · **Jalon** : J3 *(dette — résorbée là où elle commence à coûter)*

### E00US015 — Ossature de navigation de l'appli admin (coquille)
*En tant qu'* organisateur, *je veux* naviguer entre les fonctions d'administration par une **barre de navigation latérale** qui n'affiche qu'un écran à la fois, *afin de* ne plus subir une page unique où toutes les fonctions sont empilées en colonne.
- **Contexte** : le front admin est aujourd'hui **monolithique** — `frontend/src/features/competition/TrancheVerticale.tsx` empile ~14 sections dans une seule carte, gardées par `estAdmin`, **sans aucune navigation** (pas de routeur, pas de menu, tout se voit en scrollant). Deux fonctions sont même **enfouies** dans ce fichier au lieu d'être des features : l'**inscription d'un archer** (`InscriptionArcher`) et la **gestion des tournois** (`GestionTournois`, formulaires de création/édition, `CycleDeVie`). Le découpage **logique** par features existe déjà (un dossier par domaine sous `features/`) ; ce qui manque, c'est la **coquille** qui les répartit sur des écrans distincts.
- **CA — navigation** — ⚠️ **révisé le 30/07/2026 par E14US003** ([ADR-0058](../docs/adr/0058-decoupage-de-l-admin-en-trois-axes-d-activite.md)) : le regroupement **par temps du tournoi** (Préparation / Jour J / Après) a été **refusé par le commanditaire après usage** et remplacé par **trois axes d'activité** (atelier hors tournoi · pilotage · gestion), un **accueil admin** choisissant l'axe. Ne pas dériver de tests de la formulation ci-dessous, conservée pour l'historique. ~~Une **sidebar** liste les destinations d'administration **groupées par temps du tournoi**~~ ; un clic affiche **une seule destination** dans la zone principale ; **toutes** les destinations restent accessibles en permanence (`P-3`, replié ≠ interdit) ; le **sélecteur de tournoi** coiffe la navigation — tout ce qui est en dessous lui appartient.
- **CA — accueil contextualisé** (`D-20`) : l'écran affiché **par défaut** dépend du **statut** du tournoi (brouillon → préparation ; en cours → supervision ; terminé → résultats). C'est une **priorité d'affichage, pas une restriction** — les autres destinations restent à un clic.
- **CA — découpage propre** : chaque fonction d'administration est une **feature autonome** (`features/<domaine>/` : composant + `api.ts` + `hooks.ts`), branchée dans la coquille par **une seule entrée** ; **aucune** fonction n'est enfouie dans le fichier d'une autre (règle [`guide-architecture.md`](../guide-architecture.md) §8). Les deux fonctions embarquées dans `TrancheVerticale.tsx` — **inscription archer** et **gestion tournois** — sont **extraites** en features dédiées.
- **CA — l'état backend n'est pas un écran** : l'écran de diagnostic redondant (`features/systeme/EtatBackend.tsx`) est **retiré** ; l'état de connexion reste porté par la **pastille** de l'en-tête (`IndicateurConnexion`) — un voyant permanent, pas une destination.
- **CA — non-régression** : toutes les fonctions admin livrées (cycle de vie, départs, catégories, blasons, gabarits, clubs, barème, grain de validation, scoreurs, inscription, archers, placement, classement) restent **accessibles et fonctionnelles** ; aucune perte de comportement.
- **Notes** : réalise l'ossature admin du [CDC UX §7.1](../cahier-des-charges-ux.md) (`D-19`, `D-20`) et **solde le front monolithique**. **Navigation par état local `useState`** (pas de `react-router`) — arbitrage du 18/07/2026, acté en [ADR-0032](../docs/adr/0032-navigation-admin-par-etat-local.md), **remplacé le 30/07/2026 par [ADR-0059](../docs/adr/0059-routage-par-role-dans-l-url-routeur-maison.md)** (chaque monde a désormais son adresse ; le routeur reste maison) : le périmètre (≈ 16 destinations, réseau local, pas de deep-link ni d'URL partagée) ne justifie pas la dépendance (règle 11) ; à réévaluer si un vrai besoin d'URL apparaît (conséquence actée : l'état de navigation est perdu au rechargement). Le **repli en icônes** (56 px, `D-19`) réservé au plan de salle et à l'arbre de duels est **hors** de cette US. **Pattern liste/fiche** et **listes déroulantes / multisélection** des référentiels = évolution UX **séparée** (US dédiée, après la coquille), pour ne pas gonfler celle-ci. ⚠️ Le front n'a **pas de tests de rendu** : vérifier **à l'écran** que chaque destination s'ouvre et que les deux features extraites fonctionnent.
- **Arbitrages de périmètre tranchés à l'implémentation (19/07/2026), reversés ici (règle 9)** : la coquille ne matérialise **que les destinations livrées** — seuls les temps **Préparation** et **Jour J** portent des entrées ; **Après** (Podiums, Paiements, Exports, Archive, Audit) et les destinations §7.1 non encore construites (Identité, Supervision, Complétude, Validation, recherche) **n'apparaissent pas** — elles viendront avec leur US, pas en entrées vides. L'accueil contextualisé s'appuie sur les **3 statuts actuels** (les 7 d'ADR-0026 sont E01US017, non livrés) : `brouillon → « Tournoi »` ; `en_cours`/`termine → « Classement en direct »` — seul écran de suivi livré, **stand-in** de « Supervision » et « Résultats » tant que ces écrans n'existent pas. Le saut à l'accueil contextualisé se fait **au changement de tournoi**, pas à chaque changement de statut (démarrer un tournoi n'arrache pas l'admin de son écran — `P-3`). Les entrées de **rôle** (scoreur, lien poste) restent sur l'**accueil public** (hors coquille admin) : elles s'adressent à d'autres tablettes, pas au poste de l'organisateur.
- **Dépend de** : E00US011 · **Jalon** : J3 *(structure front — tirée en priorité « US suivante » à la demande de l'organisateur, 18/07/2026)*

### E00US016 — Écrans d'administration : liste → fiche & référentiels en déroulante
*En tant qu'*organisateur, *je veux* gérer chaque entité par un **tableau (liste) → fiche d'édition** et choisir les valeurs de référence dans des **listes déroulantes**, *afin de* saisir vite et sans erreur, sur des écrans propres.
- **Contexte** : après la coquille (E00US015), les écrans d'administration passent du **formulaire empilé** à un pattern **liste/fiche** homogène. Remontées du 18/07/2026. Évolution **UX transverse**, séparée de la coquille pour ne pas la gonfler.
- **CA — liste/fiche** : chaque entité du tournoi (tournois, catégories, blasons, gabarits, clubs, départs, scoreurs, archers) se gère par un **tableau** — colonnes utiles, dont l'**état** quand il existe (ex. statut du tournoi) — et une **fiche** d'édition ; on entre en édition **depuis une ligne**.
- **CA — référentiels en déroulante** : les valeurs de référence (catégories FFTA, tranches d'âge, blasons, clubs…) sont proposées en **liste déroulante** ; les champs **multivalués** (ex. catégorie ↔ **plusieurs** tranches d'âge, E01US013) se saisissent par **cases à cocher** (multisélection), jamais en texte libre.
- **CA — fractions de blason en déroulante** (remontée B3) : la **taille** d'un blason se choisit dans une déroulante **{cible entière (1), demi (½), tiers (⅓), quart (¼)}**, avec une option « Autre… » **repliée** pour un réel libre ; le back **garde le modèle fraction** (aucun changement de domaine).
- **Notes** : présentation uniquement — **aucun changement de domaine/API** attendu (au plus un confort de tri). ⚠️ Front sans tests de rendu : vérifier **à l'écran**. Découpage plus fin possible **par entité** à la planification si l'US est trop large pour une branche.
- **Dépend de** : E00US015 · **Jalon** : J3

### E00US017 — Écran d'accueil : choisir son appareil / rôle
*En tant qu'*utilisateur qui ouvre l'appli sur un appareil neuf, *je veux* un **écran de choix** au 1ᵉʳ lancement (Tablette de cible / Téléphone public / Scoreur / Admin), *afin de* déclarer explicitement mon rôle plutôt que de le déduire d'une session ouverte.
- **Contexte** : aujourd'hui l'aiguillage est **implicite** (`frontend/src/app/App.tsx`) — `estPoste` (jeton en `localStorage`, posé par le QR de cible `?poste=<code>` ou le rattachement) ouvre l'écran de poste ; sinon la coquille, qui montre l'**admin** si une session admin existe, le **public** sinon. Les trois portes existent donc déjà mais **enfouies** : le public est le défaut, l'admin est un formulaire de connexion, la tablette un lien secondaire (« Cette tablette est un poste de cible › »). L'organisateur veut les **promouvoir en choix explicites** au démarrage (demande du 20/07/2026) — plus lisible pour un bénévole qu'un rôle déduit.
- **CA — écran de choix au 1ᵉʳ lancement** : tant qu'**aucun rôle n'est posé**, l'appli présente **quatre** entrées : **Tablette (cible)**, **Téléphone (public)**, **Scoreur**, **Admin (PC)**. Le choix **persiste** (`localStorage`) : aux ouvertures suivantes l'appli va **droit** au rôle choisi, **sans réafficher l'écran** — c'est le geste initial explicite, pas un menu récurrent (`D-09` : l'archer, le plus nombreux, ne subit pas de friction à chaque ouverture). *(Arbitrage tranché à l'implémentation, le 21/07/2026 : le **scoreur** est une **4ᵉ porte** de premier niveau — cette US retire l'entrée scoreur enfouie dans l'accueil public, sans porte dédiée il deviendrait injoignable ; cf. [ADR-0042](../docs/adr/0042-modele-d-entree-choix-de-role-explicite.md).)*
- **CA — chaque choix mène où il doit** : **Tablette** → **rattachement** (QR de la cible, **ou** URL + code de rattachement + n° de cible, E04US001) puis reste un poste et **ne revoit jamais l'écran de choix ni l'admin** (`D-13` : contrôle d'accès physique — quiconque tape sur une tablette de cible est légitime) ; **Public** → l'appli publique (l'archer **et sa famille** suivent l'archer via l'écran de suivi, E07US006) ; **Scoreur** → l'entrée par **code** (E10US003), itinérante, sans cible (`D-12`) ; **Admin** → le **login** (E10US002). Le public **ne peut pas escalader** : il n'a ni code scoreur ni mot de passe admin (l'accueil public ne présente plus ni l'un ni l'autre).
- **CA — le rôle effectif : une session en cours prime sur le choix** *(précisé à l'implémentation, ADR-0042)* : le routage n'affiche l'écran de choix que si **aucune** session n'est ouverte ; une tablette rattachée ou arrivée par QR (verrou physique `D-13`, inconditionnel), puis un jeton admin ou scoreur **hérité** d'avant cette US, priment — pour qu'un rechargement ne renvoie **jamais** sur l'écran de choix (résilience jour J).
- **CA — sortie de rôle** *(tranché à l'implémentation)* : échappatoire **« Changer de rôle »** discrète (en-tête) pour Public / Scoreur / Admin → réinitialise le marqueur **et** purge les sessions locales, retour à l'écran de choix. La **tablette** en est exclue (`D-13`) : sa sortie reste le **« Détacher »** existant — mais une tablette **seulement choisie au menu et pas encore rattachée** garde l'échappatoire (sinon un mauvais tap piège l'utilisateur sans recours ; correctif de revue).
- **Notes** : **révise le modèle d'entrée de l'appli** (`D-09`/`D-10`/`D-13`, [CDC UX §3–§6](../cahier-des-charges-ux.md)) — **décision structurante ⇒ [ADR-0042](../docs/adr/0042-modele-d-entree-choix-de-role-explicite.md)** (`Accepté`, livré avec le code). Tension assumée dans l'ADR : le CDC veut que l'archer tombe sur **sa journée**, pas sur un menu (`D-09`, « GPS, pas tableau de résultats ») — acceptable car l'écran n'apparaît qu'au **1ᵉʳ lancement** puis se souvient. **Front seul** (aucun backend) ; l'**identité visuelle par tournoi** est **hors périmètre** (habillage club/neutre ici, l'identité par tournoi reste à E01US016). ⚠️ Front sans tests de rendu : vérifier **à l'écran** (3 profils/appareils isolés) — seule la logique d'aiguillage (`resoudreRole`) est testée en unitaire. Réemploi : jeton de poste (`sessionPosteStore`), login admin (`sessionAdminStore`), session scoreur (`sessionScoreurStore`), aiguillage `App.tsx`.
- **Dépend de** : E00US015, E04US001, E10US002, E07US006 · **Jalon** : J3 *(confort d'usage jour J — à planifier ; ajout du 20/07/2026)*

### E00US018 — L'atlas : le règlement en vigueur et l'histoire des décisions
*En tant que* responsable du projet, *je veux* un **site navigable** qui montre ce qui fait règle **aujourd'hui** et permet de remonter l'**histoire de chaque règle et de chaque décision**, *afin de* voir l'état réel du projet sans relire 83 ADR et 1 089 lignes de tracker.
- **Contexte** : le dépôt a grossi vite — 83 ADR, 29 règles de projet, 109 US livrées, ~56 000 lignes de backend en cinq semaines. Tout est écrit et versionné, mais rien n'est consultable d'un coup d'œil. Demande du commanditaire (15/08/2026) : *« j'ai du mal à bien suivre les règles qui sont édictées, si elles sont toujours d'actualité, si elles évoluent, du coup je ne vois pas bien l'état réel du projet, et son historique. »* Ce n'est **pas** un besoin de diagramme d'architecture : c'est un besoin de **traçabilité**.
- **CA — le règlement en vigueur** : une page présente les règles **du jour**, dans l'ordre où elles sont écrites, lisibles d'une traite, **sans historique qui parasite la lecture** (forme demandée : une « notice de jeu »). Chaque règle mène en un clic à sa fiche.
- **CA — l'histoire d'une règle** : la fiche d'une règle montre son texte actuel puis ses changements **datés**, avec leur motif, l'US et l'ADR déclencheurs. L'historique dérive de `git log -L` sur le bloc de la règle, complété des incises datées écrites à la main dans `CLAUDE.md`.
- **CA — l'identité d'une règle est stable** : une règle est identifiée par une **ancre** (`<!--regle:slug-->`), jamais par son numéro ni par son titre — sinon un réordonnancement de `CLAUDE.md` détacherait chaque historique de sa règle **sans rien casser de visible**.
- **CA — ce que le registre ne dit pas** : la page des décisions affiche, pour chaque ADR, **ce qui l'a amendé depuis**. C'est l'information manquante : 82 ADR sur 83 sont « Accepté », un seul est marqué « Remplacé », alors que 19 sont effectivement amendés — et cela n'est écrit sur aucune des deux fiches concernées.
- **CA — l'écrit confronté au code** : les chemins et symboles cités par les sections « Porté dans le code par » sont vérifiés contre le dépôt — **toutes** les sections, qu'elles soient écrites en puces **ou en tableau** (le registre emploie les deux). Un chemin disparu est **bloquant** ; un symbole introuvable est un **signal** (l'extraction reste heuristique) ; une cible non lisible symbole par symbole (un répertoire) est **signalée comme non vérifiée** plutôt que comptée pour tenue. *(Aucun chiffre n'est inscrit ici : il périmerait au prochain ADR, et la mesure vit dans le plancher de `backend/tests/test_atlas_corpus.py`, qui est vérifié. Deux revues successives ont dû corriger des comptes écrits à la main dans ce CA — d'abord parce que le lecteur ne voyait pas les sections en **tableau**, puis parce qu'il ne retenait que le **premier** module d'une entrée qui en cite plusieurs.)*
- **CA — consultable sans rien lancer** : le site s'ouvre au **double-clic** (`file://`), sans serveur, sans build et **sans aucune dépendance** ; les données générées sont commitées, et la CI échoue si elles divergent des sources.
- **Notes** : **décision structurante ⇒ [ADR-0086](../docs/adr/0086-un-atlas-genere-le-depot-cartographie-sans-dependance.md)**, qui doit se confronter à [ADR-0001](../docs/adr/0001-adopter-les-adr.md) (Markdown versionné, wiki externe rejeté) — l'atlas n'a **aucune autorité**, c'est un rendu dérivé sous porte mécanique. Schémas en **SVG maison**, aucune bibliothèque de mise en page (règle 11, précédent [ADR-0063](../docs/adr/0063-brouillon-de-format-invariant-a-l-application.md) §5 bis) : le rendu Mermaid a été **écarté par le commanditaire** (« trop de courbes et de chevauchements »). Le générateur vit dans `backend/atlas/` — hors de `backend/`, il échapperait à mypy strict, ruff et pytest. ⚠️ Le site n'a pas de test de rendu : vérifier **à l'œil** (checklist dans `atlas/README.md`). Dette assumée : `DETTE-067` (JS non typé ni linté). **Pas de fiche `docs/fonctionnel/`** : la convention vise les US qui livrent une surface dans `frontend/src/**`, ce que cette US ne touche pas — et la recette existe bien, au § « À vérifier » du fichier daté du journal (ouvrir `atlas/index.html`, cliquer une règle, ouvrir `ADR-0075` qui doit s'annoncer partiellement dépassée). *(Arbitrage tranché en revue : la dispense tient par le périmètre de la règle, pas par la checklist de `atlas/README.md`, qui est un contrôle de développeur et non une recette.)*

### E00US019 — L'atlas : l'avancement, et des livrables de suivi qui ne se contredisent pas
*En tant que* responsable du projet, *je veux* voir l'avancement d'un coup d'œil **et** être averti quand les livrables de suivi se contredisent, *afin de* ne pas repartir d'une base fausse.
- **Contexte** : `E00US018` a livré l'atlas des **règles et décisions**. Le suivi de l'avancement, lui, vit dans quatre fichiers écrits à la main — `journal-d-avancement/SUIVI-US.md` (1 100 lignes), `epics/README.md`, `stories/` et `docs/dette.md` — qui se réfèrent les uns aux autres sans que rien ne vérifie qu'ils concordent. La règle de comptage de `SUIVI-US.md` a d'ailleurs été **instituée le 08/08/2026 parce que trois compteurs sur cinq étaient faux**, chacun d'un mode différent. Et le jour même du cadrage de cette US, `main` portait un défaut réel : l'en-tête annonçait « dernière : `E05US026` » suivi d'un résumé décrivant `E05US028`. Le tracker est le **point de reprise** de « reprend les US » : un tracker faux fait repartir sur une base fausse, et c'est le seul défaut de documentation qui coûte du code.
- **CA — la vue d'avancement** : une page montre, section par section (jalons J0→J4 puis sections d'ajouts), les US avec leur **état tel que le tracker le porte** ; le **graphe des dépendances entre epics**, lu du tableau `ID | Titre | Priorité | Dépend de` d'`epics/README.md` ; et la **dette ouverte**. Une fiche par US relie ce que les quatre sources en disent : titre, état, epic, ADR qui la citent, dette qu'elle introduit ou résorbe.
- **CA — les compteurs sont recalculés, et un écart bloque** : le `n/N` écrit dans le titre de chaque section est **recalculé** selon la règle de comptage de la Légende, et tout écart est un écart **bloquant**. La règle, appliquée à la lettre : on compte les **lignes portant un identifiant d'US** ; les **US absorbées (⛔) sont exclues** ; une ligne **sans identifiant d'US** (relevé, lot hors US) ne compte **ni au numérateur ni au dénominateur** ; les lignes à `Seq = —` sont comptées **dans leur section d'origine**, jamais dans le jalon ; le numérateur est le nombre de ✅. Valeurs de référence à la livraison : **J0 12/12, J1 46/46, J2 14/14, J3 16/18, J4 0/7**. Le **total annoncé en tête** (« N US livrées ») est recalculé de même, et compte les US **distinctes** — deux US sont légitimement re-listées dans un lot d'ajouts postérieur. *(Arbitrage du 16/08/2026, reversé ici : la fiche disait `J3 12/15`, c'était faux **deux fois**. Le recalcul a d'abord trouvé 14 ✅ sur 16 lignes — en-tête non suivie du corps — puis, par le total de tête, que `E05US026` et `E05US028`, **livrées**, n'existaient que dans la **file d'attente**, un tableau en citation qu'aucun compteur ne lit. Insérées en J3, d'où `16/18`. Le contrôle du total de tête est né de ce second cas : aucun `n/N` de section ne pouvait le voir.)*
- **CA — l'état d'une US ne se déduit jamais de git** : le **glyphe du tracker fait autorité**. Piège documenté dans la Légende : `E00US016`, `E01US018` et `E01US019` ont un commit `docs(…)` dans `main` sans être livrées — une vérification qui lirait `git log` les compterait faites.
- **CA — les contradictions entre livrables sont détectées**. **Bloquant** (constat sans ambiguïté) : une US **livrée (✅)** au tracker et **absente de `stories/`** *(restreint aux ✅ le 16/08/2026 : une US planifiée mais pas encore spécifiée est un état normal du backlog — `E00US020` à `E00US022` en sont —, alors qu'on ne peut pas avoir livré ce qui n'a jamais été écrit)* ; une dépendance d'epic vers un **EPIC inexistant** ; un identifiant de dette présent **dans les deux tables** (ouverte et résorbée) **ou inscrit deux fois** ; un **total de tête** divergent du recalcul ; le **rappel de la Légende** (« J0 12/12, J1 46/46… ») divergent des sections ; un **cycle** de dépendances entre epics. **Signal** (jugement ou heuristique) : une **US portant deux états** selon la section — la colonne « État » ne dit pas partout la même chose, et trancher mécaniquement reviendrait à arbitrer un sens que le tracker n'a pas fixé ; l'US de **résorption** d'une dette absente de `stories/` ; l'US annoncée « **dernière** » dont le résumé cite un ADR qui, lui, ne cite pas cette US — c'est exactement le défaut trouvé sur `main` le 16/08.
- **CA — la porte** : les écarts **bloquants** font sortir `python -m atlas --verifier` en erreur, comme ceux d'`E00US018`. Le tracker étant le point de reprise, un compteur faux n'est pas un détail de présentation.
- **Arbitrages de la revue du 16/08/2026, reversés ici** : (a) le contrôle de **titre divergent** annoncé plus haut a été **écrit puis retiré** — mesuré, il rendait 0 vrai positif sur 2 signaux, et l'axe adversarial a construit sans effort des faux négatifs (« Supprimer un archer » concordait avec « Supprimer un club ») ; aucun seuil ne sépare un titre *reformulé* d'un titre *changé*, et un signal à la fois bruyant et poreux n'apprend qu'à ignorer la page. (b) L'en-tête du tracker **refuse d'être lu à moitié** (code 2) au lieu de rendre des champs vides : un `**` déplacé éteignait en silence le contrôle du total, et un tracker annonçant « 999 US livrées » passait au vert. (c) Trois contrôles ont été **ajoutés** sur constat de revue : `dette-numero-en-double` (le défaut réellement survenu — deux `DETTE-065` du **même** côté du registre, que `dette-dans-les-deux-tables` ne pouvait pas voir), `cycle-entre-epics` (le seul défaut que le schéma ne peut pas montrer, sa réduction transitive effaçant toutes les arêtes d'un cycle) et `recapitulatif-divergent` (la 5ᵉ écriture des mêmes compteurs, dans la Légende).
- **Recette** : `docs/fonctionnel/` **ne s'applique pas** — la convention vise les US livrant une surface dans `frontend/src/**`, pas l'atlas (précédent `E00US018`). La contrepartie est un § « **À vérifier** » dans le fichier daté du journal, qui est la recette rendue au commanditaire ; la checklist d'`atlas/README.md` est un contrôle de développeur et n'en tient pas lieu.
- **Notes** : sept variantes d'en-tête de tableau coexistent dans `SUIVI-US.md` (`Seq|US|Titre|État`, `US|Titre|Jalon|État`, `US|Titre|Épic|État`…) — le lecteur se cale sur les **colonnes présentes**, jamais sur une position. ⚠️ Le fichier **prévient lui-même** qu'il est écrit à la main et piégeux : glyphes multiples, `~~barré~~`, US absorbées, lignes hors décompte. **Échouer bruyamment sur une table mal formée** plutôt que produire un décompte faux — un décompte silencieusement faux est pire que pas de vue. Reste **hors périmètre** et gardé pour `E00US021` : confronter `docs/glossaire.md` et `docs/modele-de-donnees.md` au code. Périmètre et sévérité tranchés au cadrage du 16/08/2026 (vue **et** garde-fou ; compteurs **bloquants**).

### E00US020 — L'atlas : la carte du code
*En tant que* responsable du projet, *je veux* voir **ce que le code fait réellement des règles d'architecture** — quelle couche dépend de quelle autre, où sont les ports et qui les implémente, comment le front est découpé —, *afin de* constater la dérive au lieu de la découvrir en revue.
- **Contexte** : `E00US018` a livré le **règlement et les décisions**, `E00US019` l'**avancement**. Les deux lisent des documents. Cette tranche lit le **code**. L'écart qu'elle vise est précis : la règle 2 (« tout pointe vers le domaine ») n'est vérifiée aujourd'hui que **pour le domaine** — `backend/tests/test_domain_isolation.py` interdit au domaine d'importer les autres couches, et **rien** ne surveille les quatre autres sens. Un `application/` qui importerait `api/` passerait le hook, la CI et la revue. Côté front, la règle 10 (« organisation par features ») n'est adossée à aucun contrôle : le cadrage du 16/08/2026 a mesuré **139 arêtes feature → feature** (hors fichiers de test) et **3 nœuds d'enchevêtrement**, dont un de **19 features sur 44** — une dérive invisible parce que personne ne la regardait.
- **CA — le sens des dépendances est constaté, pas supposé** : les imports du backend sont lus à l'**AST** (`ast` de la bibliothèque standard — pas d'expression régulière : un import multi-ligne ou commenté rendrait le constat faux, et un constat faux est **bloquant**, donc coûteux). La matrice des cinq couches est confrontée au sens autorisé, dérivé des règles écrites et de rien d'autre : `domain` → **aucune** couche (règle 1) ; `application` → `domain` ; `infrastructure` → `domain`, `application` ; `api` → `domain`, `application`, `infrastructure` ; `bootstrap` → toutes (règle 8, composition root) ; et **personne n'importe `bootstrap`** — la racine de composition est un consommateur terminal, l'importer inverse le câblage.
- **CA — la matrice se lit à deux mailles** : un tableau **couche × couche** portant le nombre d'imports, et sous lui le détail **paquet × paquet** (`domain/erreurs`, `infrastructure/db`…). Toute cellule hors du sens autorisé est marquée, et chaque cellule non vide nomme les fichiers qui la peuplent — sans quoi le lecteur voit un nombre sans pouvoir le vérifier.
- **CA — les ports et leurs adapters** : les ports sont les classes dérivant de `Protocol`, et l'appariement port → adapter est **structurel** (une classe qui porte toutes les méthodes publiques du port), **jamais** par héritage : le dépôt compte des dizaines de ports pour **un seul** héritage explicite — un inventaire fondé sur les bases de classe rendrait une page vide en affirmant qu'elle est complète. La conséquence est assumée : l'appariement est une **heuristique**, un port à une seule méthode courante sur-apparie ; le nombre d'adapters candidats est donc affiché, et seul le **zéro** est signalé.
- **CA — ce que l'inventaire des ports doit dire de la règle 2** : la règle veut les ports **dans le domaine**. Un port déclaré ailleurs (`application/`) est **signalé, pas bloqué** — c'est un écart de conception qui peut être légitime (l'authentification n'est pas du métier de tir à l'arc), et le trancher mécaniquement reviendrait à arbitrer seul une question de conception. La page dit **où** est chaque port et **combien** sortent du domaine ; l'humain juge.
- **CA — le front est mesuré, en signal** : le graphe des features de `frontend/src/**` est extrait par **expression régulière** — l'atlas n'a aucune dépendance (ADR-0086) et la bibliothèque standard de Python ne sait pas lire du TypeScript. La limite est **écrite sur la page**, pas seulement en commentaire : aucun constat côté front n'est **bloquant**. Sont rendus : le nombre d'arêtes feature → feature, les **nœuds d'enchevêtrement** (composantes fortement connexes de taille > 1 — mesure définie et stable, là où « compter les cycles » dépend de l'ordre de parcours), et le **fan-in** de chaque feature, qui désigne le noyau partagé resté dans `features/`.
- **CA — la porte** : un import qui viole le sens des dépendances **backend** fait sortir `python -m atlas --verifier` en erreur, au même titre que les écarts d'`E00US018`/`E00US019`. Tout le reste — port hors domaine, port sans adapter, enchevêtrement du front — est **signal**. Justification du calibrage : le bloquant ne couvre que des constats **exacts** (AST) et **actuellement satisfaits** (mesuré au cadrage : les cinq sens sont tenus), donc la porte est verte à la livraison et ne fait que verrouiller un invariant ; les rendre bloquants sur de l'heuristique ferait rougir la CI au premier jour et la ferait désactiver.
- **CA — consultable sans rien lancer** : comme `E00US018` — page ouverte au double-clic (`file://`), données commitées, aucune dépendance, aucune ressource externe, tableaux dans un conteneur défilant.
- **Ce que l'US ne fait pas** : elle **mesure**, elle ne **corrige pas**. Les trois chantiers que la mesure révèle côté front sont inscrits au backlog **sans être implémentés** — `E00US023` (nommer le noyau partagé et casser les enchevêtrements), `E00US024` (extraire la logique pure des composants XXL), `E00US025` (le contrat DTO front ↔ back). C'est l'application du § Dette de `CLAUDE.md` : un remède structurel se traite en US dédiée, jamais en douce dans l'US courante — et ici la preuve exigée (« 3ᵉ occurrence dans le code d'aujourd'hui ») est précisément ce que cette US produit.
- **Recette** : `docs/fonctionnel/` **ne s'applique pas** — la convention vise les US livrant une surface dans `frontend/src/**`, pas l'atlas (précédents `E00US018`, `E00US019`). La contrepartie est un § « **À vérifier** » dans le fichier daté du journal.
- **Arbitrages tranchés à l'implémentation et à la revue (16/08/2026), reversés ici (règle 9)** : (a) le motif du hook `atlas-a-jour` est **élargi au code source** — l'arbitrage inverse était écrit dans la config (« laisser la CI être l'autorité »), il tenait tant que le code périmait rarement les cartes ; la carte du code renverse le rapport, presque chaque US les périme désormais. (b) **Une couche s'importe elle-même** : sans cette clause, la porte annonçait neuf violations bloquantes le jour de sa livraison, toutes fausses. (c) **Les fichiers de test sont exclus du graphe du front** : ils ne pesaient que 3 arêtes sur 142, mais ces 3 faisaient naître un **nœud entier** — or le grief fait à un nœud est qu'une feature ne peut plus être « lue, **testée** ni retirée seule », le fonder sur le test lui-même n'a pas de sens. (d) **Lire une couche absente est un refus, pas un zéro** : `rglob` sur un répertoire disparu ne lève rien, la porte serait restée verte faute d'avoir rien regardé — et le plancher agrégé des tests ne l'aurait pas vu (le dépôt passe encore `imports >= 500` sans `bootstrap`, sans `infrastructure` ou sans `api`). (e) `port-sans-adapter` a été **corrigé, pas assumé** : il rendait 0 vrai positif sur 2 signaux parce qu'il ne lisait que les méthodes, là où un port déclare en `@property` face à des champs de dataclass `frozen` (règle 4). Tout cela est porté par l'**amendement `E00US020` d'[ADR-0086](../docs/adr/0086-un-atlas-genere-le-depot-cartographie-sans-dependance.md)**.
- **Notes** : le générateur reste dans `backend/atlas/` (mypy strict, ruff, pytest) ; la lecture du front depuis un module `backend/` est assumée — l'atlas cartographie **le dépôt**, pas le backend, et ADR-0086 l'a déjà acté en lisant `stories/` et `docs/`. ⚠️ Le site n'a pas de test de rendu : vérifier **à l'œil**. Élargit `DETTE-067` (JS non typé ni linté) d'une page. **Périmètre tranché au cadrage du 16/08/2026** : backend **et** front (l'utilisateur a écarté le « backend seul » : c'est le front qui porte la dérive mesurée), vue **et** garde-fous, chantiers de correction **inscrits au backlog**. Reste hors périmètre, gardé pour `E00US022` : le rapprochement routes FastAPI ↔ appels `api.ts` (routes mortes, appels orphelins) — 4ᵉ axe, US à lui seul.

### E00US023 — Nommer le noyau partagé du front, et défaire les enchevêtrements
*En tant que* développeur, *je veux* qu'une feature du front puisse être lue, testée et retirée **seule**, *afin de* cesser de payer un couplage que personne n'a décidé.
- **Contexte** : mesure d'`E00US020`, le 16/08/2026 — **139 arêtes** (soit 228 imports) relient les features entre elles, et elles forment **3 nœuds d'enchevêtrement**, dont un de **19 features sur 44** (`archers`, `blasons`, `categories`, `competition`, `departs`, `duels`, `forfaits`, `inscriptions`, `palmares`, `patrimoine`, `phases`, `placement`, `poules`, `routage`, `saisie-duels`, `salle`, `suivi`, `suivi-deroule`, `tableaux`). *(Fichiers de test exclus : ils ajoutaient 3 arêtes, qui suffisaient à créer un 4ᵉ nœud — un enchevêtrement dû au test seul n'en est pas un.)* Deux features sortent du lot par leur **fan-in** : `competition` est importée par **18** autres, `departs` par **17**. Ce ne sont plus des features — c'est un **noyau partagé** qui n'a jamais été nommé, resté dans `features/` par habitude. La règle 10 impose l'organisation par features ; elle n'a jamais été adossée à un contrôle, et la dérive s'est installée sans qu'aucune revue ne puisse la voir.
- **CA — ce qui est transverse est nommé** : les types et fonctions réellement partagés (à commencer par ceux de `competition` et `departs`) quittent `features/` pour `shared/` (ou un `noyau/` dédié, à trancher dans l'US) ; ce qui reste dans une feature ne sert qu'à elle.
- **CA — plus aucun enchevêtrement** : `python -m atlas` ne rend plus aucun nœud de taille > 1, **ou** ceux qui restent sont explicitement justifiés et le contrôle `features-enchevetrees` devient **bloquant** sur les autres. Le passage au bloquant est la seule façon d'empêcher la dérive de revenir : c'est un invariant, pas un nettoyage ponctuel.
- **CA — aucun changement visible** : rendu et comportement **strictement inchangés** à l'écran ; c'est un déplacement de fichiers et d'imports, pas une évolution.
- **Cas nommé — `departDeSalle` (`features/salle/rotation.ts`)** *(ajouté le 18/08/2026, relevé aux revues d'`E05US031`, axes C2 et adversarial)* : helper **pur et testé** qui répond à « quel créneau tire en ce moment ». Il est importé par **10 features** — `competition`, `departs`, `en-cours`, `forfaits`, `placement`, `routage`, `salle`, `suivi`, `suivi-deroule`, `tableaux` ; `en-cours` est la dernière arrivée. *(Liste **recalée le 18/08/2026** en revue d'`E05US031`, axe A : elle citait `supervision` et `tournois`, qui n'importent pas ce helper, omettait `departs`, et nommait la feature neuve `phases-publiques` — un nom que l'US n'a finalement pas retenu.)* C'est exactement le motif de cette US : **un vocabulaire partagé resté dans `features/` par habitude**, du même genre que ce que le projet a déjà domicilié dans `shared/salle/place.ts` et `shared/phases/catalogue.ts`. Déplacement **mécanique** vers `shared/salle/`, sans changement de comportement — un bon premier geste de l'US, et un bon candidat si elle est redécoupée. ⚠️ **Inscrit ici plutôt qu'en US propre** : la règle du projet veut qu'on **élargisse la ligne existante** au lieu d'ouvrir un contournement local, et une US dédiée à un seul `git mv` aurait fait diverger l'ADR « où vit le partagé » que celle-ci doit rendre.
- **Notes** : **décision structurante ⇒ ADR** (où vit le partagé, et pourquoi le front n'a pas de couches horizontales — le serveur est autoritaire, un « domaine » front serait une seconde source de vérité). ⚠️ Front sans tests de rendu : vérifier **à l'écran**, destination par destination. ### E00US024 — Sortir la logique des quatre composants XXL du front
*En tant que* développeur, *je veux* que la logique des plus gros écrans soit **testable sans les rendre**, *afin qu'*une régression de calcul ne parte pas en production faute de test possible.
- **Contexte** : `Deroule.tsx` (1 056 lignes), `SaisieDuels.tsx` (915), `CoquilleAdmin.tsx` (642), `Saisie.tsx` (641). Le front **n'a pas de tests de rendu** — un ⚠️ répété dans presque toutes les US front — donc tout ce qui vit dans un composant est **hors de portée des tests**. Le dépôt sait pourtant déjà faire l'inverse : `saisie/volees.ts`, `brouillons.ts`, `horsLigne.ts`, `rejeu.ts` sont des fonctions pures, chacune couverte par son fichier de tests. C'est le même geste, appliqué là où il ne l'a pas été.
- **CA — la logique quitte le composant** : pour chacun des quatre écrans, les décisions (dérivations d'état, tris, agrégations, règles d'affichage conditionnel) passent dans des **fonctions pures** d'un module voisin ; le composant ne garde que le rendu et le branchement des gestes.
- **CA — et elle est testée** : chaque fonction extraite est couverte par des tests unitaires **dérivés du comportement actuel** (non-régression : l'oracle *est* le comportement d'aujourd'hui, règle 9).
- **CA — aucun changement visible** : rendu et comportement strictement inchangés.
- **Notes** : ne vise **pas** une couverture du rendu (pas de testing-library ici — ce serait une autre US, et une dépendance de plus). Découpage **par composant** conseillé à la planification : quatre tranches indépendantes, dont aucune n'a besoin des autres.

### E00US025 — Le contrat DTO front ↔ back, vérifié plutôt que recopié
*En tant que* développeur, *je veux* qu'un champ renommé côté serveur **casse quelque chose de visible**, *afin de* ne pas le découvrir le jour du tournoi.
- **Contexte** : les **39 `api.ts`** du front recopient **à la main** les DTO Pydantic du backend (« miroir backend », dit leur en-tête). Rien ne relie les deux : TypeScript vérifie que le front est cohérent avec **sa propre déclaration**, jamais avec le serveur. Renommer un champ dans un DTO backend laisse le front compiler, les tests verts, le lint vert — et l'écran se vide **à l'exécution**, sur le réseau local, sans internet pour aller chercher de l'aide. C'est le risque le plus cher des trois : les deux autres coûtent de la maintenabilité, celui-ci casse un usage réel le jour J.
- **CA — l'écart se voit avant la production** : un mécanisme mécanique confronte les DTO servis par FastAPI (schéma OpenAPI) aux interfaces déclarées dans `frontend/src/features/**/api.ts`, et **échoue** sur un champ absent, renommé ou de type incompatible. Il tourne en CI.
- **CA — l'arbitrage de la voie est explicite** : deux options, à trancher **avec l'utilisateur** car l'une ajoute une dépendance (règle 11) — (a) **générer** les types depuis l'OpenAPI (`openapi-typescript` ou équivalent : moins de code maison, une dépendance de plus, et des types générés à committer) ; (b) un **test de conformité** maison qui lit `openapi.json` et les interfaces déclarées (aucune dépendance, un lecteur TypeScript heuristique à écrire et à maintenir). Ne pas trancher seul.
- **Notes** : le périmètre peut se restreindre aux endpoints du **jour J** (saisie, duels, classement, placement) si l'US est trop large — c'est là que la casse coûte le plus. ⚠️ La voie (a) demande une décision **avant** de coder : ne pas brancher sans réponse.
- **Dépend de** : — · **Jalon** : hors jalon *(risque jour J, révélé par la mesure du 16/08/2026)*

### E00US026 — Rallier le JavaScript de l'atlas à l'outillage du front
*En tant que* développeur, *je veux* que le JavaScript de l'atlas passe sous les mêmes outils que le reste du dépôt, *afin de* ne pas maintenir 1 800 lignes que rien ne relit.
- **Contexte** : **résorption de [`DETTE-067`](../docs/dette.md#dette-067--le-javascript-de-latlas-nest-ni-typé-ni-linté)**, dont le déclencheur explicite (« `atlas/statique/` dépasse 2 000 lignes ») a été **franchi le 16/08/2026 par `E00US020`** : 2 367 lignes (1 837 de JS, 530 de CSS). `eslint` et `prettier` sont cadrés sur `^frontend/` (hooks pre-commit) et `working-directory: frontend` (CI) ; `atlas/`, à la racine, leur est invisible. La dette prévoyait la sortie : la prochaine US qui touche `atlas/statique/` **ouvre** la résorption au lieu de relever le seuil — c'est précisément pour ne pas renégocier au cas par cas que le seuil avait été écrit à l'avance.
- **CA — le linter et le formateur voient l'atlas** : `atlas/statique/*.js` et `atlas/*.html` passent sous `eslint` et `prettier`, en pre-commit **et** en CI, par **élargissement des patrons existants** (`^(frontend|atlas)/`) — pas par une seconde chaîne Node, pas par un build (règle 12).
- **CA — la configuration reconnaît ce que ce code est** : script classique de navigateur (pas de module ES, `var`, IIFE, globales `window`/`document`) — la configuration ESLint du front étant taillée pour du TS/React, elle ne s'applique **pas telle quelle** ; l'US pose la configuration adaptée (`env: browser`, `parserOptions` sans modules) plutôt que de désactiver les règles une par une.
- **CA — zéro régression du site** : `backend/tests/test_atlas_site.py` reste vert (pas de `fetch()`, pas de module ES, aucune ressource externe, `viewport` présent) — c'est le contrat qui rend le site ouvrable au double-clic hors ligne.
- **CA — la dette change de table** : marqueurs `DETTE-067` retirés des trois fichiers, ligne déplacée en « Dette résorbée ».
- **Notes** : ⚠️ la première exécution rendra probablement des **centaines** d'avertissements sur du code écrit sans linter — arbitrer entre corriger et calibrer la configuration fait partie de l'US, et le résultat ne doit pas être une liste de `eslint-disable`. Le **typage** (TS) reste **hors périmètre** : la dette parle de « ni typé ni linté », et rallier le linter suffit à lever le déclencheur — typer demanderait un build, ce que la règle 12 refuse pour un site de documentation. ### E00US027 — Le code porte des pointeurs, pas le raisonnement
*En tant que* développeur, *je veux* que le raisonnement vive dans la documentation et non recopié dans le code, *afin de* ne plus lire des phrases que rien ne vérifie et qui ont divergé.
- **Contexte** : le commentaire est le seul artefact que **rien ne contrôle** — ni le compilateur, ni `mypy`, ni `eslint`, ni un test. Mesure du 27/08/2026 : **13 %** de commentaire sur les 106 450 lignes de production, ce qui est sain en moyenne, mais la distribution est très inégale — **45 fichiers dépassent 40 %** et quatre dépassent **60 %** (`shared/ui/pagination.ts` à 68 %). En lisant ce que ces fichiers contiennent, le volume ne vient pas du *pourquoi* mais de **copies** : historique de revue (« relevé en 2ᵉ passe, axe C2 »), CA recopiés mot pour mot, raisonnements d'ADR dupliqués, archéologie de création de module. Une copie diverge — c'est le mécanisme qui a produit, en revue d'`E16US009`, une section d'ADR nommant un test inexistant et trois commentaires sur-promettants réécrits trois fois. Décision : [ADR-0099](../docs/adr/0099-le-code-porte-des-pointeurs-pas-le-raisonnement.md), règle 13 de `CLAUDE.md`.
- **CA — la règle est écrite là où on la lit** : `CLAUDE.md` porte les **trois tests de survie** d'un commentaire (contrainte non déductible / avertissement / renvoi d'une ligne) et la liste de ce qui sort, avec le lieu où chaque chose vit déjà.
- **CA — aucune connaissance n'est détruite** : toute phrase retirée est **vérifiée présente ailleurs** (ADR, story, registre de dette, test) ; si elle n'y est pas, elle y est **déplacée d'abord**. Le nettoyage range, il ne supprime pas.
- **CA — un lot démonstratif est traité** : les fichiers de ≥ 100 lignes de commentaire **et** ≥ 50 % (`shared/ui/pagination.ts`, `shared/phases/catalogue.ts`, `shared/phases/relance.ts`, `features/completude/Completude.tsx`), plus `features/competition/TableClassement.tsx` — retenu bien qu'à 34 %, parce qu'il est l'échantillon le plus chargé en narration de revue (trois passes viennent de l'y déposer).
- **CA — le comportement ne change pas** : aucune ligne exécutable modifiée, porte mécanique complète verte. C'est le seul garde-fou possible sur ce genre d'US, et il est suffisant : ce qui n'est pas du commentaire n'est pas touché.
- **Notes** : ⚠️ **le pourcentage désigne où regarder, il ne condamne pas** — un fichier à 60 % peut être légitime si la règle métier qu'il porte est subtile. ⚠️ **Les docstrings de test gardent leur statut** : un test énonce son oracle, ce qu'il prouve et ce qu'il ne prouve pas — c'est une contrainte non déductible. ⚠️ Le reste des 45 fichiers se traite **au fil de l'eau** (toute US qui touche un fichier le nettoie), pas en big bang : un diff de 45 fichiers est irrelisable, et `E16US009` vient d'en administrer la preuve. ⚠️ Limite connue et non fermée : rien ne vérifie qu'un renvoi `cf. ADR-00xx` pointe un ADR qui existe et dit bien cela — l'atlas contrôle l'inverse.
- **Dépend de** : — · **Jalon** : hors jalon *(qualité de lecture, arbitrée le 27/08/2026)*
